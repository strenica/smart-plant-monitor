# Smart Plant Monitor

An ESP32 sensor node and a Raspberry Pi 4 vision node monitoring a plant's
health, built as a ladder of four energy-management variants so the energy cost
of each technique can be measured rather than guessed.

Course project for FRI, 2026.

Setting this up from bare boards? See [INSTALL.md](INSTALL.md).

## Hardware

| Part | Notes |
|---|---|
| ESP32-D0WD-V3 | 4 MB flash, dual core + LP core |
| Raspberry Pi 4 Model B | 4 GB, Debian 13 (trixie) |
| DHT11 | temperature and humidity |
| DFRobot SEN0114 | **resistive** soil moisture, two prongs |
| Grove Buzzer | passive piezo, driven at its 2300 Hz resonance |
| Raspberry Pi Camera Module 3 | Sony IMX708, 12 MP |
| Monsoon HVPM | power measurement, 5 kHz |

## How the two boards are connected

| ESP32 | Pi | Purpose |
|---|---|---|
| D25 (GPIO25) | pin 5 (GPIO3) | wake, open-drain, 250 ms low pulse |
| GND | pin 6 | common ground |
| TX2 (GPIO17) | pin 10 (RXD) | ESP32 → Pi |
| RX2 (GPIO16) | pin 8 (TXD) | Pi → ESP32 |
| USB | USB | power, and the UART0 console |

Never touch Pi pins 2 and 4 — they are 5 V.

## The four variants

Each rung moves one decision from the expensive node to the cheap one. The Pi
idles at about 3 W and the ESP32 at about 0.1 W, so the Pi is the whole game.

| | Sample interval | Rules on | Camera | Pi |
|---|---|---|---|---|
| V0 baseline | 2 s | Pi | never | always on |
| V1 fixed duty cycle | 60 s | Pi | every 5 min | always on |
| V2 adaptive sampling | 10 s / 10 min | ESP32 | on event + heartbeat | always on |
| V3 deep sleep | 60 s / 10 min | ESP32 | one per wake | off between events |

The only firmware difference between two variants is
`variants/<name>/variant.h`. Everything else is shared, so the diff between two
rungs is a dozen lines and the comparison stays honest.

## Layout

```
install.sh         build, flash and deploy one variant
variants/          one folder per rung of the ladder
  v0_baseline/     variant.h, run.py, install.sh, README.md

  v2_adaptive/
  v3_deepsleep/

  main/

    variant.h      generated by install.sh from variants/<name>/

    dht11.c        bit-bang one-wire driver (ESP-IDF has no official one)
    buzzer.c       LEDC PWM at 2300 Hz
    pi_link.c      wake pulse + UART2
    rules.c        ESP32-side rule engine, used by V2 and V3
pi/                Raspberry Pi side
  common/config.py configuration.txt and reading parsers
  common/rules.py  rule evaluation, edge triggering, cooldown
  common/logger.py events_log.txt writer
  common/camera.py shared camera settings and capture
  v0_baseline.py   V0: poll, evaluate, log
  v1_duty.py       V1: the same, plus a picture every five minutes
  v2_adaptive.py   V2: log and photograph on event
  v3_wake.py       V3: one picture per wake, then halt
  vision/          U2-Net leaf pipeline
config/            configuration.txt, camera.json
tools/             flash, preview and live-view helpers
```

## Install a variant

One command builds the firmware with that variant's knobs, flashes it on the Pi
at 115200 baud, syncs the Pi code, installs both systemd units and starts the
monitor:

```bash
./install.sh v1_duty
```

```bash
./install.sh --list                  # show the four variants
./install.sh v1_duty --fw-only       # firmware only
./install.sh v1_duty --pi-only       # Pi code only
./install.sh v1_duty --no-flash      # build, do not flash
./install.sh v1_duty --no-service    # skip the monitoring unit
./install.sh v1_duty --no-dashboard  # skip the dashboard unit
./install.sh v1_duty --local         # build and flash on the Pi itself
./install.sh v1_duty --pi user@host  # target a different Pi
```

Run it on the Pi and it notices by itself: no SSH, no rsync, no copying.
`--local` needs ESP-IDF on the Pi; see [INSTALL.md](INSTALL.md).

Flashing cold-boots the ESP32, which is the same thing as pressing EN, so the
install ends with the camera preview open on port 8080. Frame the shot and press
**save and apply**, or leave it alone and it gives up after five minutes and
starts monitoring.

Each `variants/<name>/` folder also works on its own:

```bash
./variants/v1_duty/install.sh
```

The ESP32 is wired to the Pi, so the build happens on the workstation and only
the binaries travel. Flashing uses `--no-stub` at 115200 baud: this board's
CP2102 fails to start the stub flasher at any baud, and the ROM loader is slower
but reliable.

## Run

On the Pi:

```bash
cd ~/plant
.venv/bin/python variants/v1_duty/run.py --dry-run
```

`--dry-run` evaluates and logs without buzzing. Drop it to drive the buzzer.

## Setup mode: press EN to reframe

Pressing EN on the ESP32 cold-boots it, and it remembers that. Two paths lead
into setup mode:

- **Pi booting** — the supervisor asks `mode?` and gets `mode setup`.
- **Pi already running** — the ESP32 sends `setup` over UART2, the variant exits
  with code 42, and the supervisor switches to the preview.

```
esp32 mode: setup
setup mode: preview on port 8080, giving up after 300 s with no browser
```

The camera preview runs instead of the monitoring loop, so you can reframe
without fighting the scanner for the camera. It ends when you press **save and
apply**, or after five minutes with no browser connected. Either way the
monitoring loop starts afterwards, so a forgotten preview cannot leave the plant
unwatched.

The flag lives in the ESP32's RTC memory and is cleared once framing is done, so
the next boot goes straight to monitoring. A power cycle clears it too.

In V3 the Pi is halted, so the ESP32 wakes it on a cold boot and then stays
awake until the Pi says `mode run`. Without that it would deep sleep before the
Pi finished booting, the flag would never clear, and every later boot would land
in the preview again. Setup mode is also the only moment the two nodes are awake
together, so it is when the supervisor hands the ESP32 the intervals from
`configuration.txt`.

## Dashboard

`./install.sh <variant>` installs a small web UI on port 8081: the latest sensor
values, the event log, and an editor for `configuration.txt` that validates
before saving. It shows the last frame the scanner analysed rather than a live
stream, because only one process can hold the camera and the monitoring loop
needs it.

Two frames, side by side: the capture as it came off the camera, and the same
frame with the leaf regions the model found outlined in red and each verdict
written on. The second one is what makes a log line like `G=0.99 B=0.00
healthy-ish` checkable — you can see whether the model picked the leaf or the
wall behind it.

Saving restarts `plant-monitor`, because the variant loops read the config once
at startup and a saved file otherwise does nothing until the next reboot. The
restart is skipped while the camera preview is up, since the preview runs under
that same unit and restarting it would kill a framing session mid-way.

## configuration.txt

```
1: air_humidity > 50
2: air_temperature < 15
3: soil_humidity < 300

sample_interval = 60
image_interval = 300
heartbeat = 3600
adaptive_fast = 10
adaptive_slow = 600
log_max_lines = 50000
```

The rule number is the buzz count: rule 2 buzzes twice. A rule buzzes when it
*enters* violation, then re-alerts once per cooldown (30 min by default) while
it stays violated. Clearing a condition is silent.

The `key = value` lines set the intervals, in seconds. They are optional: a
missing key falls back to the variant's compiled default, so a file with only
rules still runs. An unknown key is an error rather than a silent no-op, because
a typo that quietly leaves the old interval in place is worse than a crash.

`sample_interval` is pushed to the ESP32 over UART2 when the Pi starts, so
changing it does not need a reflash. The ESP32 keeps it in RTC memory, which
survives deep sleep but not a power cycle. `adaptive_fast` and `adaptive_slow`
are only used by V2 and V3, `image_interval` only by V1, and `heartbeat` only by
V2.

`log_max_lines` caps `logs/events_log.txt`. The file is trimmed to the newest
N lines when a run opens it, and again whenever it grows to twice that, so it
never sits far above the limit. `0` keeps everything. At V1's rate (three
sensor lines a minute) 50000 lines is about eleven days; the dashboard only
shows the newest 25.

## Vision

`pi/vision/leafs.py` runs the U2-Net saliency model to isolate leaf-like
foreground, then applies hand-written colour rules.

```bash
cd ~/plant/pi/vision
~/plant/.venv/bin/python leafs.py
~/plant/.venv/bin/python leafs.py --image images/pepper_bacterial_spot.jpg
```

The split between learned and hand-written stages is the point:

| Stage | Kind |
|---|---|
| Saliency map | learned (U2-Net, 7 outputs, first one used) |
| Otsu threshold, morphology, component filtering | hand-written |
| HSV colour fractions, health label | hand-written |

So `healthy-ish` is a colour heuristic, not a diagnosis. On the bundled
samples it reports `healthy-ish` for both the healthy pepper and the bacterial
spot one, because the spots are a small fraction of leaf area. That is a
limitation of the rule, not a bug in the model.

### Calibrating the colour rule

The hue bands live in `config/vision.json` and are editable from the dashboard's
**vision** page. Hue is OpenCV's 0..179 scale, so 30 is 60 degrees; saturation
and value are 0..255.

Every leaf logs its measured `H`, `S` and `V` alongside the fractions:

```
vision leaf 1: G=0.00 Y=0.00 B=0.74 H=19 S=16 V=122 stressed-ish
```

That is what you tune against. A leaf scoring zero on all three bands has a hue
outside every range, and the numbers tell you which way to widen.

Two things make the measurement unstable, and both are settings:

- **`awb`** in `config/camera.json`. Auto white balance re-decides per capture,
  and on a dark leaf it can pick a large blue gain — enough to turn a brown leaf
  blue. Set `"awb": "off"` with `colour_gains` to lock it. Two captures then
  measure identically, which is the only way a band means anything.
- **`autofocus`**. With it off the lens sits at infinity, the leaf is a blurry
  blob, and the average colour is a blend of leaf and background.

A very dark leaf is hard for any colour rule: the signal is low, so the
illuminant and the sensor noise dominate the hue. Bright, even lighting and a
leaf that fills the frame give the rule the best chance.

**`u2netp.onnx` is included**, so the repository runs as cloned. It is the
unchanged model from the course's `leafs-starter.zip`; that archive's
`ASSETS.json` records that the export provenance and licence are not documented
in the original project, and names the architecture as U²-Net
(https://github.com/xuebinqin/U-2-Net). It is committed here because this
project cannot run without it, and it is used only for the course it was
supplied for — not offered as a general-purpose asset.

## Camera preview

The Pi is headless, so the preview is served over HTTP and viewed in a browser:

```bash
cd ~/plant
.venv/bin/python tools/preview.py
# open http://10.42.0.15:8080/
```

Settings live in `config/camera.json` and are shared with the leaf scanner, so
what you frame in the browser is what gets analysed.

| Key | Meaning |
|---|---|
| `size` | output resolution |
| `sensor_mode` | `[2304, 1296]` uses the whole sensor |
| `rotation` | 0, 90, 180 or 270 |
| `zoom` | 1.0 is the full frame, 2.0 crops to the middle half |
| `crop` | region of interest as `[x, y, w, h]` in 0..1 fractions |
| `autofocus` | continuous AF; off leaves the lens at infinity |
| `awb` | `auto` or `off`; `off` locks `colour_gains` |
| `colour_gains` | `[red, blue]` multipliers, used when `awb` is `off` |
| `preview` | set `false` to disable the server |
| `preview_port`, `preview_fps` | server settings |

### Leaf check

The **leaf check** button opens a panel that freezes the current frame, runs the
saliency model on it once, and then lets you drag the hue bands and watch the
verdict change. Only the colour rule re-runs per slider move — about 13 ms — so
it is genuinely live rather than a re-analysis of a new frame each time.

The panel shows the annotated frame, the fractions, the verdict, and the
measured H, S and V. When a band looks right, copy the numbers into
`config/vision.json` (or the dashboard's vision page) to make it permanent.

**`sensor_mode` matters.** The Camera Module 3 offers three modes and picamera2
picks the fastest by default, which is a centre crop of the sensor — the preview
looks zoomed in. `[2304, 1296]` uses the whole sensor.

### Framing controls

The page has live controls. Adjust them while watching, then press **Save and
apply**: that writes `config/camera.json` and shuts the server down, freeing the
camera for the scanner. Tick "disable preview after saving" to set
`preview: false` at the same time.

| Control | Effect |
|---|---|
| **Rotate** 0/90/180/270 | applied per frame, instant |
| **Zoom** slider 1.0–3.0 | crops the centre and scales back, instant |
| **Size** dropdown or custom W×H | reconfigures the camera (~1 s) |
| **Drag on the image** | sets the crop region, instant |
| **Crop → Clear** | back to the whole frame |
| **Save and apply** | writes the config, stops the server |

**Crop is the one that actually saves work.** It produces a genuinely smaller
output image — a half-width crop really is half the pixels, so less ISP work,
less JPEG encoding and less memory bandwidth. Zoom only changes framing; it
scales back to the same output size.

To preview again afterwards, either set `"preview": true` or pass `--force`:

```bash
.venv/bin/python tools/preview.py --force
```

**Only one process can hold the camera.** Stop the preview before running
`leafs.py --camera`:

```bash
fuser -k 8080/tcp
```

### Does a smaller image save power?

Only a little, and crop is the only part that helps. The sensor still runs at
2304×1296 and the model input is always 320×320, so inference cost is unchanged
whatever you capture. What you save is ISP work, JPEG encoding and memory
bandwidth — real, but small next to the cost of *how often* you capture. The
frequency is the lever that matters.
