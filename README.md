# Smart Plant Monitor

An ESP32 sensor node and a Raspberry Pi 4 vision node monitoring a plant's
health, built as a ladder of four energy-management variants so the energy cost
of each technique can be measured rather than guessed.

Course project for FRI, 2026.

## Hardware

| Part | Notes |
|---|---|
| ESP32-D0WD-V3 | 4 MB flash, dual core + LP core |
| Raspberry Pi 4 Model B | 4 GB, Debian 13 (trixie) |
| DHT11 | temperature and humidity |
| DFRobot SEN0114 | **resistive** soil moisture, two prongs |
| Grove Buzzer | passive piezo, driven at its 2300 Hz resonance |
| Raspberry Pi Camera Module 3 | Sony IMX708, 12 MP |
| Monsoon HVPM | power measurement, 5 kHz |

## How the two boards are connected

| ESP32 | Pi | Purpose |
|---|---|---|
| D25 (GPIO25) | pin 5 (GPIO3) | wake, open-drain, 250 ms low pulse |
| GND | pin 6 | common ground |
| TX2 (GPIO17) | pin 10 (RXD) | ESP32 → Pi |
| RX2 (GPIO16) | pin 8 (TXD) | Pi → ESP32 |
| USB | USB | power, and the UART0 console |

Never touch Pi pins 2 and 4 — they are 5 V.

## The four variants

Each rung moves one decision from the expensive node to the cheap one. The Pi
idles at about 3 W and the ESP32 at about 0.1 W, so the Pi is the whole game.

| | Sample interval | Rules on | Camera | Pi |
|---|---|---|---|---|
| V0 baseline | 2 s | Pi | never | always on |
| V1 fixed duty cycle | 60 s | Pi | every 5 min | always on |
| V2 adaptive sampling | 10 s / 10 min | ESP32 | on event + heartbeat | always on |
| V3 deep sleep | 60 s / 10 min | ESP32 | one per wake | off between events |

The only firmware difference between two variants is
`variants/<name>/variant.h`. Everything else is shared, so the diff between two
rungs is a dozen lines and the comparison stays honest.

## Layout

```
install.sh         build, flash and deploy one variant
variants/          one folder per rung of the ladder
  v0_baseline/     variant.h, run.py, install.sh, README.md
  v1_duty/
  v2_adaptive/
  v3_deepsleep/
firmware/          ESP-IDF project for the ESP32, shared by all four
  main/
    config.h       pin map and soil calibration
    variant.h      generated by install.sh from variants/<name>/
    sensors.c      DHT11 + ADC, with the soil probe's power gate
    dht11.c        bit-bang one-wire driver (ESP-IDF has no official one)
    buzzer.c       LEDC PWM at 2300 Hz
    pi_link.c      wake pulse + UART2
    rules.c        ESP32-side rule engine, used by V2 and V3
pi/                Raspberry Pi side
  common/config.py configuration.txt and reading parsers
  common/rules.py  rule evaluation, edge triggering, cooldown
  common/logger.py events_log.txt writer
  common/camera.py shared camera settings and capture
  v0_baseline.py   V0: poll, evaluate, log
  v1_duty.py       V1: the same, plus a picture every five minutes
  v2_adaptive.py   V2: log and photograph on event
  v3_wake.py       V3: one picture per wake, then halt
  vision/          U2-Net leaf pipeline
config/            configuration.txt, camera.json
tools/             flash, preview and live-view helpers
```

## Install a variant

One command builds the firmware with that variant's knobs, flashes it on the Pi
at 115200 baud, and syncs the Pi code:

```bash
./install.sh v1_duty
```

```bash
./install.sh --list               # show the four variants
./install.sh v1_duty --fw-only    # firmware only
./install.sh v1_duty --pi-only    # Pi code only
./install.sh v1_duty --no-flash   # build, do not flash
./install.sh v1_duty --service    # also install a systemd unit
```

Each `variants/<name>/` folder also works on its own:

```bash
./variants/v1_duty/install.sh
```

The ESP32 is wired to the Pi, so the build happens on the workstation and only
the binaries travel. Flashing uses `--no-stub` at 115200 baud: this board's
CP2102 fails to start the stub flasher at any baud, and the ROM loader is slower
but reliable.

## Run

On the Pi:

```bash
cd ~/plant
.venv/bin/python variants/v1_duty/run.py --dry-run
```

`--dry-run` evaluates and logs without buzzing. Drop it to drive the buzzer.

## configuration.txt

```
1: air_humidity > 50
2: air_temperature < 15
3: soil_humidity < 300
```

The rule number is the buzz count: rule 2 buzzes twice. A rule buzzes when it
*enters* violation, then re-alerts once per cooldown (30 min by default) while
it stays violated. Clearing a condition is silent.

## Vision

`pi/vision/leafs.py` runs the U2-Net saliency model to isolate leaf-like
foreground, then applies hand-written colour rules.

```bash
cd ~/plant/pi/vision
~/plant/.venv/bin/python leafs.py
~/plant/.venv/bin/python leafs.py --image images/pepper_bacterial_spot.jpg
```

The split between learned and hand-written stages is the point:

| Stage | Kind |
|---|---|
| Saliency map | learned (U2-Net, 7 outputs, first one used) |
| Otsu threshold, morphology, component filtering | hand-written |
| HSV colour fractions, health label | hand-written |

So `healthy-ish` is a colour heuristic, not a diagnosis. On the bundled
samples it reports `healthy-ish` for both the healthy pepper and the bacterial
spot one, because the spots are a small fraction of leaf area. That is a
limitation of the rule, not a bug in the model.

**`u2netp.onnx` is not in this repo** — its provenance and licence are not
recorded in the source project, so it is not redistributed. Unzip
`leafs-starter.zip` and copy it into `pi/vision/`.

Sample photographs: Mohanty, Hughes and Salathe / PlantVillage, CC BY-SA 3.0.

## Camera preview

The Pi is headless, so the preview is served over HTTP and viewed in a browser:

```bash
cd ~/plant
.venv/bin/python tools/preview.py
# open http://10.42.0.15:8080/
```

Settings live in `config/camera.json` and are shared with the leaf scanner, so
what you frame in the browser is what gets analysed.

| Key | Meaning |
|---|---|
| `size` | output resolution |
| `sensor_mode` | `[2304, 1296]` uses the whole sensor |
| `rotation` | 0, 90, 180 or 270 |
| `zoom` | 1.0 is the full frame, 2.0 crops to the middle half |
| `preview` | set `false` to disable the server |
| `preview_port`, `preview_fps` | server settings |

**`sensor_mode` matters.** The Camera Module 3 offers three modes and picamera2
picks the fastest by default, which is a centre crop of the sensor — the preview
looks zoomed in. `[2304, 1296]` uses the whole sensor.

### Framing controls

The page has live controls. Adjust them while watching, then press **Save and
apply**: that writes `config/camera.json` and shuts the server down, freeing the
camera for the scanner. Tick "disable preview after saving" to set
`preview: false` at the same time.

| Control | Effect |
|---|---|
| **Rotate** 0/90/180/270 | applied per frame, instant |
| **Zoom** slider 1.0–3.0 | crops the centre and scales back, instant |
| **Size** dropdown or custom W×H | reconfigures the camera (~1 s) |
| **Drag on the image** | sets the crop region, instant |
| **Crop → Clear** | back to the whole frame |
| **Save and apply** | writes the config, stops the server |

**Crop is the one that actually saves work.** It produces a genuinely smaller
output image — a half-width crop really is half the pixels, so less ISP work,
less JPEG encoding and less memory bandwidth. Zoom only changes framing; it
scales back to the same output size.

To preview again afterwards, either set `"preview": true` or pass `--force`:

```bash
.venv/bin/python tools/preview.py --force
```

**Only one process can hold the camera.** Stop the preview before running
`leafs.py --camera`:

```bash
fuser -k 8080/tcp
```

### Does a smaller image save power?

Only a little, and crop is the only part that helps. The sensor still runs at
2304×1296 and the model input is always 320×320, so inference cost is unchanged
whatever you capture. What you save is ISP work, JPEG encoding and memory
bandwidth — real, but small next to the cost of *how often* you capture. The
frequency is the lever that matters.
